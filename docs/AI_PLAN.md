# Career Quest: AI, оценка и следующие проверки

Состояние интеграции: 23 сентября 2026. Приложение использует интерфейс Next.js,
отдельный backend workspace и PostgreSQL. AI-код, baseline и evaluation находятся
в `backend/`; `frontend/` отвечает за интерфейс. HTTP, авторизация, импорт и
симуляция выполнения реализованы, поэтому дальнейшая работа — проверка качества
и всего сценария, а не создание ещё одного серверного контура.

## Что проверяет AI-часть

Приложение рекомендует 1–3 следующих действия из допустимого каталога. Сервер
строит snapshot сотрудника, проверяет роль, грейд, предварительные требования,
историю и расписание. Он же рассчитывает эффекты навыков и прогресс. Модель
выбирает идентификаторы кандидатов и проверенные факты для объяснения; свободный
текст модели, новые курсы и придуманные приросты в результат не принимаются.

| Часть | Источник |
|---|---|
| HTTP и авторизация | `backend/src/http/index.ts` |
| Получение snapshot, защита параллельных запросов, повторная проверка версии | `backend/src/services/recommendations.ts` |
| Допуск, изменения навыков, факты и условные будущие эффекты | `backend/src/domain/index.ts` |
| Граница выбора и fallback | `backend/src/ai/recommend.ts` |
| Один HTTP-адаптер провайдера | `backend/src/ai/adapter.ts` |
| Проверка ссылок на кандидатов и факты | `backend/src/ai/response-validator.ts` |
| Ранжирование baseline | `backend/src/domain/baseline.ts` |
| Сигналы истории и проверка полноты evidence | `backend/src/domain/baseline-signals.ts`, `backend/src/domain/recommendation-evidence.ts` |
| Авторские случаи и метрики | `backend/evaluation/cases.ts`, `backend/evaluation/metrics.ts` |
| CLI оценки | `backend/scripts/evaluate-ai.ts` |
| Регрессии оценки | `backend/tests/team-ai/evaluation.test.ts` |

`recommend(input, { signals, emptyReason?, signal? })` работает с уже проверенным
снимком. Он не открывает БД и не проверяет сессию. Пустому набору нужен конкретный
`emptyReason` от доменного слоя; модель в этом случае не вызывается. После
завершения выбора HTTP-сервис повторно проверяет `dataset_revision` и
`employee_revision`: результат старого снимка не выдаётся как актуальный.

Для каждого кандидата передаются обе карты baseline-сигналов, включая явные
нули. Пропущенный сигнал или некорректные факты — ошибка подготовки snapshot;
такой случай не должен превращаться в правдоподобный fallback. Для каждого
доступного кандидата проверяются непустые уникальные факты как минимум из трёх
основных категорий: грейд, разрыв навыков, история, требования цели.

Baseline учитывает закрытие критических разрывов, прирост до требований цели,
условную пользу подготовительного шага, последние релевантные исходы обучения
и трудозатраты. Посторонний навык и рост выше требования цели не завышают целевую
пользу. Будущий прирост открываемой активности учитывается со скидкой при выборе,
но не начисляется за подготовительный курс. Fallback сохраняет все необходимые
факты, включая отдельный факт об открываемом следующем шаге.

## Как запустить оценку

Из корня репозитория после установки зависимостей:

```sh
npm run eval:ai
npm run eval:ai -- --json
```

По умолчанию выполняется только deterministic baseline на семи авторских
синтетических случаях. Даже если ключ уже настроен, этот режим не обращается
к провайдеру и не использует официальный набор. В отчёте стоит `baseline_only`;
метрики качества AI и доля fallback остаются `null`, поскольку AI не запускался.

Для проверки провайдера должны быть заданы **оба** параметра `LLM_API_KEY` и
`LLM_MODEL` в корневом `.env` или окружении процесса. Приложение и CLI используют
один адаптер, `LLM_API_URL` и ограничение `LLM_TIMEOUT_MS`. Бюджет адаптера
ограничен максимумом 8 секунд; это не обещание времени всего HTTP-сценария.

```sh
npm run smoke:ai
npm run eval:ai -- --live --json
```

`smoke:ai` явно включает `--live --smoke` и отправляет один авторский случай.
`--live` без `--smoke` отправляет семь случаев последовательно. `--smoke` без
`--live` отклоняется, отсутствие ключа или модели тоже завершается понятной
ошибкой. Живой прогон использует API и может расходовать средства провайдера.

Workspace-команда запускает `tsx --env-file-if-exists=../.env
scripts/evaluate-ai.ts` из каталога `backend/`, используя загрузку env в Node 24.
Зависимость от `@next/env`, `frontend/.env.local`, Next-сервера или работающей БД
для авторской evaluation отсутствует. JSON-отчёт можно сохранить обычным
перенаправлением stdout; ключи и исходные ответы провайдера в отчёт не попадают.

## Сценарии и смысл метрик

Семь заранее описанных сценариев проверяют:

1. Критический разрыв против самого низкого, но постороннего навыка.
2. Историю пропусков при одинаковой полезности двух действий.
3. Большой нецелевой прирост против полезного целевого шага.
4. Ограничение пользы уровнем требования, без премии за превышение.
5. Подготовительный шаг с нулевым прямым прогрессом и конкретным будущим эффектом.
6. Сохранение ID уже начатого участия и его прошлой даты.
7. Произвольные новые идентификаторы, включая Unicode.

Для каждого случая отчёт показывает выбранный top-1, независимо рассчитанный
baseline top-1, соответствие авторскому ожиданию, допустимость ссылок на факты,
версию snapshot, время вызова границы `recommend` и размер подготовленного payload.
Это не замер полной загрузки страницы, запроса к БД или сети браузера.

`acceptedAi` требует режима `ai`, валидных ссылок и той же версии снимка.
Успешный fallback не считается принятым ответом AI и не увеличивает согласие
AI с baseline. Доли правильного выбора AI и совпадения с baseline используют
только принятые AI-ответы в знаменателе. Если таких ответов нет, качество AI
остаётся `null`, а причины отказа и fallback учитываются отдельно.

Live-команда возвращает ненулевой exit code при fallback, невалидных ссылках или
версии, отклонении от авторского ожидаемого выбора либо времени более 10 секунд.
Offline-команда проверяет ожидания baseline, ссылки и версию. Это строгая
регрессионная проверка наших правил: допустимый иной выбор модели может
потребовать экспертного разбора, а не автоматически означать низкую пользу.

Семь случаев созданы вместе с правилами, поэтому даже результат 7/7 не доказывает
превосходство модели, готовность к реальной эксплуатации или оценку жюри.
Валидность ссылок подтверждает использование фактов из snapshot, а не
независимую истинность исходных кадровых данных.

При переносе evaluator локально прошли 22 теста `evaluation.test.ts`, а offline
CLI удовлетворил всем 7 авторским ожиданиям с валидными ссылками и версиями.
Отдельный запуск с фиктивными настройками провайдера и блокировкой любого вызова
`fetch` подтвердил, что offline-режим не обращается в сеть. Проверены ненулевые
exit codes для `--smoke` без `--live` и live-режима без ключа/модели. Настоящих
вызовов модели в этой проверке не было.

## Что проверить следующим

| Проверка | Критерий |
|---|---|
| Live smoke выбранного провайдера | Принятый ответ AI с измеренным временем; fallback показан отдельно |
| Независимый holdout | Новые случаи зафиксированы до следующей настройки правил и prompt |
| Слепое сравнение | Эксперт сравнивает минимальный навык, baseline и AI по полезности следующего шага |
| Контрфактическая история | Изменение только истории даёт объяснимое изменение выбора без вывода о мотивации |
| Сквозной HTTP-путь | Профиль → рекомендация → однократная симуляция → новый прогресс и HR |
| Гонки и сбои | Повтор completion не начисляет навык дважды; старый AI-ответ отклоняется; таймаут даёт явный fallback |
| Импорт и чистая поставка | Новый профиль работает без правки кода; состояние сохраняется после рестарта |

Результаты текущего запуска фиксируются в выводе CLI и тестов. Исторические
результаты отдельной ветки команды не следует представлять как проверку
текущей интеграции. Пока живой прогон не выполнен, заявления о качестве модели
и её преимуществе над baseline остаются непроверенными.
