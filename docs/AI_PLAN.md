# Career Quest: проверка AI и оставшиеся ограничения

Обновлено 23 сентября 2026. Рабочая реализация находится в `backend/`, интерфейс —
в `frontend/`, данные — в PostgreSQL. Результаты текущей конфигурации и команды
воспроизведения: [AI_VERIFICATION.md](AI_VERIFICATION.md), [AI.md](AI.md).

## Решение и основания

Использовать готовую модель через API, проверяемые серверные факты и полноценный
fallback на правилах. Обучение весов модели для текущего объёма не требуется.
Модель выбирает 1–3 существующих шага и ссылки на факты; допуск, прирост, история,
версии и запись completion остаются обязанностью backend.

В текущей проверке выбран `gpt-6-sol` с `reasoning_effort=low`: 17 авторских случаев
в трёх повторах прошли все 51 проверки выбора, ссылок, решающих фактов и явно
размеченного порядка. Время границы recommend: p50 2,38 с, p95 3,80 с, max 5,09 с.
Исходный gpt-4o-mini на более раннем наборе дал 24/28 полных прохождений; ошибки
касались условной пользы и её объяснения. Это разные конфигурации и частично
разные наборы, а не контролируемое сравнение только архитектур моделей.

## Проверка сильных предположений

| Утверждение | Контраргумент и вывод |
|---|---|
| Модель соблюдает правила | 51/51 подтверждает эти вызовы; последующие ответы могут отличаться. Сохраняем строгую валидацию и fallback. |
| LLM полезнее baseline | Не доказано: prompt задаёт ту же эвристику, сервер передаёт её числовые факторы и уже сортирует кандидатов. Согласие измеряет соблюдение правил. |
| Все карточки качественные | На всех случаях проверяется допустимость, на одном размеченном multi-card случае — полный выданный порядок. Экспертной оценки всех альтернатив нет. |
| Факты истинны | Проверена согласованность с серверным snapshot. Это не независимая проверка качества исходных кадровых данных. |
| Быстрый адаптер означает быстрый продукт | Время recommend не включает браузер. Отдельно проверяются реальные PostgreSQL и HTTP handlers; TCP-проверка описана в отчёте. |
| Тестовые профили доказывают обобщение | Все случаи авторские; часть создана после разбора ошибок. Это регрессионные/приёмочные проверки, не скрытый независимый holdout. |

## Исправленные причины ошибок

- Модели передаются рассчитанные числовые факторы, а не задача пересчитать их по прозе.
- Факт истории и штраф используют один отбор трёх терминальных исходов до даты среза.
- Каждое открываемое событие имеет отдельный факт о будущем эффекте после подготовки;
  этот эффект не становится уже полученным навыком.
- Отдельная проверка требует решающий факт и для прямого шага, выигравшего за счёт unlock.
- Занятые LLM-запросы используют отдельный пул соединений; GET профиля не ждёт модель.
- Отмена HTTP-запроса доходит до транспорта, advisory lock освобождается.
- Live CLI не выдаёт успешный fallback за успех AI; сохраняются неудачные отчёты.

## Что ещё требует внешних данных

1. Проверка полного официального набора и профилей жюри локально. В этом checkout
   официальных четырёх входных файлов нет; они не подменены синтетическими.
2. Независимая экспертная разметка полезности и слепое сравнение baseline/AI.
   Решение о дополнительной ценности LLM пересматривается по этим результатам.
3. Запуск итоговой поставки другим участником на целевой машине с официальными файлами.
   Production build прошёл; локальный TCP/browser smoke в этой сессии отклонён
   автоматической проверкой запуска процесса (`blocked by policy`).
4. До отправки официальных данных в облачный API — подтвердить допустимость по правилам
   организаторов. Текущие живые прогоны отправляли только самостоятельно созданные данные.

Не нужны дополнительные игровые функции, обучение модели или второй AI-движок,
чтобы закрыть перечисленные проверки.
