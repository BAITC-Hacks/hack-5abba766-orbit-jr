# Качество рекомендаций и диагностика каталога

Подбор использует серверный расчёт допустимых активностей и их эффекта. AI выбирает
существующих кандидатов и ссылается на проверенные факты; при недоступности модели
возвращается явно обозначенный подбор по правилам. Рост навыков, ограничения
аудитории и запись результатов остаются в доменном коде.

## История похожих активностей

Помимо истории конкретного события, в объяснение входит история других добровольных
активностей, развивающих хотя бы один тот же навык. Наблюдения разделены по тому же
и другому формату. Учитываются только записи выбранного сотрудника до даты среза,
за предшествующий календарный год. Каждая группа содержит не более шести последних
итоговых наблюдений: завершение, отказ, неявка или прекращение.

В тексте указаны число наблюдений, знаменатели и период. При количестве меньше трёх
данные обозначены как недостаточные. Отсутствие истории не считается отказом;
причины пропусков и предпочтения человека из этих данных не устанавливаются.
Исходные record ID сохраняются во внутреннем результате агрегации, но не выводятся
в пользовательский текст. Для самостоятельного обучения дата источника является
датой зачисления: отдельный completed_at в исходной схеме отсутствует.

Подбор по правилам сравнивает кандидатов последовательно:

1. Число полностью закрываемых критических разрывов.
2. Прямой взвешенный прирост к цели плюс половину лучшей открываемой будущей пользы.
3. Число негативных исходов последних трёх итоговых попыток той же активности.
4. Долю отказов, неявок и прекращений среди похожих активностей того же формата,
   только если таких наблюдений не меньше трёх.
5. Длительность, продолжение уже начатого участия и стабильные идентификаторы.

Эта доля — описательный признак для разрешения равенства, а не обученная вероятность
завершения. Недостаточная выборка даёт нулевой штраф и не доказывает предпочтение.
В исходном локальном наборе на момент проверки ни у одного кандидата не оказалось
достаточного числа таких негативных наблюдений для ненулевого штрафа. Изменение
выбора проверено на отдельных авторских профилях; улучшение качества на исходных
200 сотрудниках этим не заявляется.

## Подготовительные шаги

Для каждой открываемой активности сервер добавляет отдельный факт: изменение навыков
после её самостоятельного завершения и дополнительное покрытие цели. Сначала
применяется эффект подготовительного шага, затем рассчитывается следующий.
Будущая польза не начисляется заранее и не суммируется между альтернативными
рекомендациями. Расписание и допуск следующего шага проверяются заново после
выполнения текущего.

## HR и покрытие каталога

HR API возвращает catalog_gaps — группы по навыку и причине. Диагностика различает:

- отсутствие добровольной активности с положительным эффектом по навыку;
- отсутствие подходящей текущей роли или грейда в аудитории;
- достигнутый предел уровня у соответствующих аудитории активностей.

Для группы видны число сотрудников, число критических потребностей и переходы к
профилям. Уже начатое доступное участие сохраняет первоначальный допуск. Проверка
описывает структуру каталога: она не гарантирует доступную дату, выполнение
предварительных требований или полный маршрут. Отсутствие следующего шага не
считается оценкой результативности сотрудника. История для HR индексируется по
сотруднику до расчёта, чтобы не сканировать историю всей компании для каждого
кандидата.

## Параллельные запросы и кэш

В одном процессе выполняется не более трёх подборов одновременно. Остальные разные
запросы получают RECOMMENDATION_BUSY с HTTP 429 и понятным предложением повторить
запрос. Одинаковые вызовы без `AbortSignal` разделяют одну выполняющуюся работу.
HTTP-запросы с сигналом независимы, чтобы отмена одного не прерывала чужой подбор;
сигнал проходит до адаптера. Advisory lock защищает одну employee/version и между
процессами: конфликт даёт HTTP 429 `RECOMMENDATION_IN_PROGRESS`. Для блокировок
выделен отдельный пул с пределом 10 соединений; обычный пул также имеет предел 10.
Ожидание подключения к AI-пулу ограничено секундой, затем возвращается HTTP 503
`STORAGE_BUSY`. Транзакция не удерживается во время вызова модели.

Успешный AI-ответ хранится в памяти не более 60 секунд, максимум 128 записей.
Ключ является хэшем сотрудника, полного входного снимка и сигналов, версии, лимита, промпта,
схемы и конфигурации провайдера. Перед обращением к кэшу читается текущее состояние
и проверяется ожидаемая версия. Ошибки, устаревшие ответы и fallback не кэшируются.
Это локальный кэш одного процесса; перезапуск его очищает. Содержимое профиля и
ключ провайдера не записываются в текст ключа кэша или журналы.

## Проверка

Из корня репозитория:

```sh
npm test
npm run eval:ai
npm run eval:ai -- --suite=domain --json
npm run eval:ai -- --suite=all --json
```

Без выбора набора запускаются семь исходных сценариев `regression`. Набор `domain`
содержит шесть сценариев из авторских исходных профилей и истории: они проходят
настоящие схемы данных, проверку связей и доменный подбор. В нём дополнительно
проверяются два состояния без кандидатов. `--suite=all` включает также восемь
`challenge` и два `acceptance`: всего 23 случая ранжирования и два пустых результата. Тесты
сверяют фактическое изменение навыков после моделирования выполнения с обещанным
эффектом карточки, проверяют неизвестные ID и чужие факты.

```sh
npm run smoke:ai
npm run eval:ai -- --live --suite=all --repeat=3 --json
```

Live-команды требуют LLM_API_KEY и LLM_MODEL. Они отправляют только авторские
синтетические сценарии. Отчёт отдельно показывает принятые AI-ответы, fallback,
совпадение с авторским ожидаемым выбором и с baseline. p50/p95 относятся только к
вызову ранжирования: HTTP, БД и браузер в них не входят. Эти проверки не измеряют
вовлечённость сотрудников или экономический эффект.

Сохранённый [командный живой отчёт](AI_VERIFICATION.md) относится к прежним
17 случаям без набора `domain`; он не подтверждает настройку AI текущего запуска.

Перед демонстрацией дополнительно проверяются чистый Compose-запуск, импорт новых
профилей и истории, цикл выполнения и сохранение после рестарта. Требования UI до
двух секунд и AI до десяти секунд проверяются на полном HTTP-сценарии отдельно от
offline evaluation.
