# Бэкенд Career Quest

**Реализован отдельный TypeScript-workspace `backend/`, который исполняется в процессе Next.js и хранит данные в PostgreSQL.** Он содержит доменные расчёты, API, сессии, импорт, миграции и симуляции. Отдельный сервер приложения помимо Next не требуется; PostgreSQL запускается вторым сервисом Docker Compose.

Общие типы находятся в [contracts/backend.ts](../contracts/backend.ts), обзор — в [ARCHITECTURE.md](ARCHITECTURE.md), команды поставки — в корневом [README](../README.md). Этот документ описывает текущую реализацию и её ограничения. Адаптер AI реализован и проверяется с контролируемыми ответами; работа реального провайдера без ключа не подтверждена.

## 1. Назначение и данные

Основной сценарий: открыть сотрудника → выбрать карьерную цель → получить 1–3 обоснованных альтернативы следующего шага → смоделировать выполнение → увидеть пересчёт навыков и рекомендаций → проверить общий HR-срез. HR может добавить профили и историю из файлов без изменения кода.

Официальный набор: **200 сотрудников, 40 активностей, 60 навыков, 32 профиля требований и 2 743 участия**. Дата сценария берётся из метаданных; для выданного набора это `2026-10-01`. Она не заменяется системной датой. Сессии и аудит, наоборот, используют реальные часы.

Сохранены особенности источника:

- Навыки сотрудника отражают последнюю оценку, а не нулевое состояние до всей истории.
- Отсутствующий навык равен нулю. Активность даёт ограниченный прирост, вычисляемый кодом.
- Обязательные активности исключены из добровольных рекомендаций и симуляций, но остаются в истории и HR-статистике. Повторные обязательные записи допустимы.
- `EV_036` — повторяемый клуб; завершения разных сессий различаются по дате.
- Несколько `in_progress` одного события — отдельные попытки с разными ID. Например, это есть у `E0009` для `EV_035`.
- Ранее начатое участие может относиться к прежнему грейду: оно сохраняет допуск, как у `E0181` для `EV_022`.
- Для самостоятельного курса отдельной даты завершения нет: исходная `date` используется как явно принятое приближение.

Идентификаторы не ограничены исходным диапазоном. Схемы допускают новые профили в том же формате; правила импорта описаны ниже.

```text
backend/src/validation/index.ts          JSON/CSV-схемы, нормализация, связи

```

Runtime — Node.js 24; UI — Next.js 16/React 19; база — PostgreSQL 18. Drizzle описывает схему и предоставляет типизированный DB-handle, а текущие операции хранилища выполняют параметризованный SQL через `pg`. Zod проверяет входные данные, `csv-parse` разбирает CSV с BOM и кавычками, Vitest запускает тесты.

`frontend/` и `backend/` — два npm-workspace с одним корневым lock-файлом. Устанавливать зависимости следует из корня репозитория. Пакет `backend` импортируется Next как серверный код; API-ключи и соединение с БД не попадают в браузер.

HTTP-слой проверяет запрос, права и формат, вызывает сервис и упаковывает ответ. Доменный слой — чистые функции: он не импортирует Next, ORM и SDK модели. Сервисы управляют транзакциями. Файловый загрузчик отделён от HTTP-модулей: production build не читает официальный датасет и не подключается к БД.

## 3. Хранение

У состояния три слоя: **неизменяемый источник → локальные изменения → вычисляемое представление**. Исходные JSON/CSV не перезаписываются. Текущие уровни навыков вычисляются, а не дублируются отдельным изменяемым полем.

| Таблица | Содержимое и ограничения |
|---|---|
| `schema_migrations` | Применённые версии SQL-миграций |
| `app_meta` | Единственная строка: дата среза, dataset/global revisions, seed marker, fingerprint, шкала навыков |
| `employees` | ID, исходный JSONB, canonical hash, employee revision |
| `skills`, `role_profiles`, `events` | Неизменяемый каталог; ключ профиля роли — `(role, grade)` |
| `history_records` | ID исходной попытки, FK сотрудника и активности, дата, статус, JSONB и hash |
| `goal_overrides` | Выбранная цель или null, actor, время; одна запись на сотрудника |
| `demo_completions` | Сотрудник, событие, исходное участие или null, occurrence key, две даты, actor и sequence |
| `action_receipts` | Уникальный `(actor, operation, idempotency_key)`, hash запроса и исходный ответ |
| `import_batches` | ID пакета, actor, fingerprint, счётчики и revisions результата |
| `audit_records` | Кто изменил цель, выполнил симуляцию или импортировал данные |
| `accounts`, `sessions` | Demo-аккаунты, хэши паролей, хэши случайных session token, expiry |

PostgreSQL обеспечивает внешние ключи и уникальность. В `demo_completions` уникален ненулевой `participation_id` и тройка `(employee_id, event_id, occurrence_key)`. Для неповторяемого события occurrence key равен `once`, для клуба — дате сессии. Исходные завершения дополнительно проверяются сервисом в той же транзакции. Обязательная история не ограничена правилом одного завершения.

Есть индексы истории по сотруднику/дате и событию/статусу, симуляций по сотруднику/sequence и сессий по expiry. Вложенные значения хранятся в JSONB, перед записью проходят проверку схемы и связей.

## 4. Снимки и конкурентные изменения

`readSnapshot()` открывает короткую транзакцию **`REPEATABLE READ READ ONLY`**. Метаданные, справочники, история, цели и симуляции читаются из одного согласованного состояния; после чтения соединение освобождается, расчёты выполняются в памяти.

Каждая изменяющая бизнес-операция начинает `BEGIN` и блокирует единственную строку `app_meta` через `SELECT … FOR UPDATE`. После получения блокировки сервис читает актуальное состояние, проверяет версии и выполняет изменение. **Все доменные записи сейчас сериализованы**, включая изменения разных сотрудников. Это упрощает защиту импорта и симуляций на текущем объёме; параллельные записи по сотрудникам пока не реализованы.

Обычная транзакция имеет lock timeout 3 секунды и statement timeout 15 секунд. При соответствующем timeout, deadlock или конфликте сериализации сервис возвращает `503 STORAGE_BUSY`. Для bootstrap установлены более длинные пределы. В транзакциях используются асинхронные запросы PostgreSQL; внешних HTTP-вызовов и ожидания модели внутри них нет.

| Счётчик | Когда изменяется |
|---|---|
| `dataset_revision` | Импорт реально добавил исходные данные |
| `employee_revision` | Изменена цель, добавлена симуляция или импортирована новая история существующего сотрудника |
| `global_revision` | Любое изменяющее goal/completion/import-действие |

Новый сотрудник начинает с employee revision 1. Идентичный импорт, повтор receipt и повторная установка уже сохранённого override счётчики не увеличивают. `DomainVersion` состоит из dataset и employee revisions; HR-ответ содержит global revision.

## 5. Проекция навыков

`employeeView(snapshot, id)` применяет данные в таком порядке:

1. Исходные `employees.skills` на `last_review_date`; отсутствующий навык — 0.
2. Исходные `completed`, где `last_review_date < date <= as_of_date`, по `(date, record_id)`.
3. Локальные симуляции по `sequence`.

На второй стадии читается именно source status. Исходный `in_progress`, отображаемый завершённым из-за симуляции, не начисляется ещё раз. Равенство даты завершения дате исходной оценки не даёт нового исторического прироста; локальная симуляция применяется, поскольку произошла после загрузки baseline.

Для каждого эффекта:

```text
delta = max(0, min(gain, max_level - current_level, 5 - current_level))
after = current_level + delta
```

Уровень выше `max_level` не уменьшается. Частичное прохождение, score и отказ сами по себе навыков не прибавляют. Исторические завершения не пересматриваются по нынешнему грейду: ограничения аудитории нужны для нового действия.

## 6. Цель и прогресс

Приоритет цели: локальный override → импортированная цель → предложение следующего грейда текущей роли → отсутствие цели. Выбор null сбрасывает явную цель, после чего возможно предложение следующего грейда; оно обозначается как `suggested`. Lead без цели не получает выдуманный следующий грейд.

Явная целевая пара `(role, grade)` должна существовать в каталоге и может относиться к другой профессии. Достижение требований автоматически не меняет должность или грейд.

```text
gap[skill] = max(0, required - current)
coverage = sum(min(current[skill], required[skill])) / sum(required[skill])
```

Считаются положительные требования цели. Coverage — доля 0–1; при отсутствии цели progress равен null. В API эффект рекомендации — разница долей, UI переводит её в процентные пункты. 100% означает покрытие перечисленных навыков, а не гарантию повышения.

## 7. Допуск и подготовительные шаги

**Start:** добровольное событие, подходящие текущие роль и грейд, выполненные prerequisites, доступная будущая сессия либо self-paced без даты, отсутствие уже завершённого такого события/сессии. Если участие уже начато, используется continue.

**Continue:** конкретная исходная запись `in_progress`, принадлежащая сотруднику. Грейд, prerequisites и расписание не проверяются заново; начатое участие сохраняет допуск. Проверяются добровольность, отсутствие завершения и положительный прирост. Из нескольких открытых попыток рекомендация выбирает последнюю по `(date, record_id)`.

После завершения одной попытки остальные попытки того же неповторяемого события сохраняются в источнике, но получают `actionable=false` и `superseded_by`. Они исключаются из эффективных счётчиков участия и отдельно учитываются как superseded.

Целевая профессия влияет на требования, текущая — на аудиторию нового события. `remote` не запрещает offline автоматически: географии и запрета поездок в источнике нет.

Кандидат бывает прямым (`direct`) или подготовительным (`prerequisite`). Для второго проверяется один шаг вперёд: доступный A повышает навыки так, что ранее недоступный из-за prerequisites B становится допустимым и сокращает целевой разрыв. Если оба новых шага идут по расписанию, B должен иметь сессию позже выбранной сессии A. Для самостоятельного или уже начатого A дата завершения неизвестна, поэтому открытие B условно и расписание нужно перепроверить после выполнения A.

`unlocks_event_ids` отражает эту связь. У подготовительного шага непосредственный `goal_coverage_delta` может быть 0. Общий полезный курс без подтверждённой связи с целью не выдаётся как карьерная рекомендация.

Пустые состояния: `GOAL_REQUIRED`, `GOAL_REACHED`, `NO_ELIGIBLE_EVENTS`, `NO_BENEFICIAL_EVENTS`, `NO_GOAL_RELEVANT_EVENTS`. Это отдельные причины, а не ошибка модели или оценка мотивации сотрудника.

## 8. Ранжирование и AI

Детерминированный baseline сравнивает:

1. Число полностью закрытых критических разрывов.
2. Прямую взвешенную пользу + 0,5 × максимальную пользу открываемого следующего шага.
3. Меньшее число негативных исходов среди последних трёх завершённых/прерванных/пропущенных/отклонённых попыток того же события.
4. Меньшую длительность, затем стабильные ID.

Вес критического навыка — 2, остальных — 1. Это продуктовая эвристика, не обученная метрика. Негативная история не создаёт вечного запрета, отсутствие истории явно обозначается.

Сервер передаёт AI роль, грейд, цель, навыки и допустимых кандидатов с подготовленными фактами. ФИО, руководитель, полные профили других сотрудников и свободные исходные описания не передаются. Модель возвращает только ID кандидатов, ID фактов и необязательный ID альтернативы.

Адаптер использует серверные `LLM_API_URL`, `LLM_API_KEY`, `LLM_MODEL` и Chat Completions с JSON Schema. Проверяется структура, 1–limit уникальных выборов, принадлежность ID текущему снимку, минимум три категории фактов из `grade/skill_gap/history/target_requirement`, а также корректность альтернативы. Альтернатива должна быть допустимым, но не выбранным кандидатом. Текст объяснения и числа берутся из проверенных серверных фактов.

Каждая из 1–3 карточек — альтернатива следующего шага из одной версии профиля. Складывать их эффекты как готовый последовательный план нельзя. После выполнения рекомендации пересчитываются.

## 9. Вызов AI, блокировки и сбои

Вызов провайдера ограничен timeout не более 8 секунд (`LLM_TIMEOUT_MS` может его уменьшить). Общая задержка включает чтение БД и вычисления; целевые 10 секунд не являются измеренной гарантией для любой нагрузки.

Для `(employee, dataset_revision, employee_revision)` сервис получает **session-level PostgreSQL advisory lock** через `pg_try_advisory_lock`. Повторный одновременный подбор получает `429 RECOMMENDATION_IN_PROGRESS`. Соединение остаётся занятым на время вызова модели, но транзакция БД не открыта. В `finally` lock освобождается; при ошибке освобождения соединение уничтожается.

После ответа на том же соединении читается новый repeatable-read snapshot. Изменение версии даёт `409 STALE_RECOMMENDATION`, без повторного платного запроса и без выдачи устаревших карточек. Изменения другого сотрудника сами по себе не инвалидируют результат; импорт меняет общую dataset revision.

| Режим | Значение |
|---|---|
| `ai` | Провайдер ответил, структура и факты приняты валидатором |
| `rules_fallback` | Нет ключа/модели, timeout, ошибка провайдера или невалидный ответ; использован baseline |
| `no_candidates` | Доменный расчёт не нашёл следующего шага; провайдер не вызывался |

Ключ остаётся серверным. `ai_configured` в health означает наличие ключа и модели, а не успешное соединение. Реальный вызов провайдера и превосходство AI над baseline ещё требуется проверить с доступным ключом; mock/unit-проверки этого не доказывают.

## 10. Симуляции и идемпотентность

Все новые выполнения требуют `simulation=true`. Сохраняются дата сессии, фиксированная сценарная `applied_as_of` и реальная `recorded_at`. Будущую сессию можно смоделировать сейчас; приложение не заявляет о реальном посещении.

Запрос содержит существующий `participation_id` либо новый event/session. Для self-paced дата равна null, для нового события по расписанию выбирается существующая сессия не раньше даты сценария. Клиент не передаёт прирост навыков: сервер рассчитывает его заново.

Порядок записи:

1. HTTP проверяет сессию, scope, Origin и схему. Для completion и committing import нужен `Idempotency-Key`.
2. Сервис открывает транзакцию и блокирует `app_meta`.
3. Проверяет receipt actor/operation/key **до expected version**. Hash включает операцию, target из URL и нормализованное тело, включая версию. Идентичный запрос возвращает прежний результат; другое тело/target — `IDEMPOTENCY_CONFLICT`.
4. Проверяет актуальную версию, принадлежность участия, допуск, сессию и отсутствие завершения в источнике/симуляциях.
5. Записывает completion, увеличивает revisions, рассчитывает профиль, сохраняет receipt и audit в одной транзакции.
6. Возвращает результат; при replay исходная версия сохраняется, `meta.replayed=true`.

Другой ключ не позволяет повторно начислить ту же активность. Возможны `ALREADY_COMPLETED`, `SESSION_ALREADY_COMPLETED`, `USE_EXISTING_PARTICIPATION`. Ошибка откатывает и данные, и receipt. Goal использует expected version, но отдельного idempotency receipt для него нет.

## 11. Импорт

`POST /api/import` принимает multipart с `employees` JSON и/или `history` CSV, `expected_dataset_revision`, `dry_run`. Суммарный размер файлов — до 20 МиБ, до 1 000 профилей и 50 000 строк истории. Должен быть хотя бы один непустой файл. CSV проверяет заголовки и число столбцов; пустые числовые поля и due_date становятся null. JSON сотрудников сохраняет официальный формат `{meta, employees}` и должен иметь дату активного среза.

Проверяются схема, даты, числовые диапазоны, согласованность процента со статусом, роли/грейды, цели, навыки, руководители и FK истории. Ссылки разрешаются против объединения существующих данных и пакета, поэтому можно загрузить нового сотрудника вместе с его руководителем.

Правило записи — **add-or-identical**:

- Новый ID добавляется.
- Полностью идентичная нормализованная запись пропускается по canonical hash.
- Изменённая запись с существующим ID и повтор ID внутри файла считаются конфликтом.

Импорт источника не заменяет goals/completions. Повтор исходного `in_progress` после симуляции остаётся идентичным источником, а новое completed того же неповторяемого события/сессии конфликтует с историей или симуляцией, чтобы не начислить навыки дважды. Повторные обязательные записи сохраняются.

Предварительная проверка возвращает ошибки связей/конфликтов без записи; синтаксически невалидный файл отклоняется ещё при разборе. Commit с конфликтами отклоняется целиком. Успешный пакет сохраняет строки, revisions, batch, receipt и audit атомарно. Идентичный пакет не меняет revisions. Это не механизм редактирования или удаления существующих профилей.

## 12. HTTP-контракт и права

Успешный ответ: `{data, meta: {request_id, as_of_date, replayed?}}`. Ошибка: `{error: {code, message, details?}, request_id}`. Для персональных ответов установлен `Cache-Control: private, no-store`.

| Метод и маршрут | Доступ | Действие |
|---|---|---|
| `GET /api/health` | Без входа | Готовность БД/схемы/seed и наличие AI-конфигурации |
| `POST /api/auth/login` | Без входа | Вход, установка cookie |
| `GET /api/auth/session` | Вошедший | Текущая роль и employee ID |
| `POST /api/auth/logout` | Вошедший | Удаление серверной сессии и cookie |
| `GET /api/catalog` | Вошедший | Навыки, требования и активности |
| `GET /api/employees` | HR | Поиск/фильтры, offset/limit, список сотрудников |
| `GET /api/employees/:id` | Сам сотрудник или HR | Рассчитанный профиль |
| `PUT /api/employees/:id/goal` | Сам сотрудник или HR | Выбор/сброс цели |
| `POST /api/employees/:id/recommendations` | Сам сотрудник или HR | Подбор следующего шага |
| `POST /api/employees/:id/completions` | Сам сотрудник или HR | Симуляция выполнения |
| `GET /api/hr/overview` | HR | Общий срез |
| `POST /api/import` | HR | Проверка/добавление источника |

HR может изменять цель и симулировать выполнение за сотрудника для демонстрации импортированных профилей. Actor и target сохраняются раздельно. Это явно ограниченная demo-модель полномочий.

Два начальных аккаунта: сотрудник, связанный с первым по ID профилем, и HR. Пароли хэшируются scrypt, token создаётся криптографически случайно, в БД хранится только его SHA-256 hash. Cookie: HttpOnly, SameSite=Lax, Path=/; Secure включается при HTTPS в APP_ORIGIN. TTL — 12 часов реального времени.

Изменяющие запросы, включая login, проверяют Origin; для локального APP_ORIGIN допускается соответствующий алиас localhost/127.0.0.1. JSON требует application/json и ограничен 64 КиБ. API не включает произвольный CORS. Лимитер входа хранится в памяти процесса: он не распределённый и сбрасывается при перезапуске. UI регистрации/администрирования новых аккаунтов и SSO не реализованы.

Логи содержат request ID, метод, путь, длительность и безопасный тип ошибки. Пароли, cookie, ключи, полные импорты и prompts не логируются.

## 13. HR-аналитика

`hrOverview(snapshot)` использует те же `employeeView` и `getCandidates`, что кабинет сотрудника. Вызовов модели нет.

- Дефициты навыков группируются по источнику цели. Знаменатель — сотрудники этой группы, чья цель требует данный навык, а не вся компания.
- Сотрудники без следующего шага сопровождаются причиной. Отсутствие цели и достигнутая цель не объявляются отсутствием мотивации.
- Исходные counts всех статусов, число симуляций и эффективные сценарные counts различаются.
- Superseded-попытки остаются в источнике, исключаются из эффективных counts и учитываются отдельно.
- Срез содержит global revision. Рейтинга «качества людей» и кадровых прогнозов нет.

## 14. Bootstrap и Docker

В Compose два сервиса: `db` на PostgreSQL и `app` на Node.js 24/Next. Приложение ждёт healthcheck БД, затем запускает отдельный bootstrap перед HTTP. Корневой Docker context содержит оба workspace и contracts; зависимости ставятся через корневой lock. Runtime использует непривилегированного пользователя node.

Порядок bootstrap:

1. Получить advisory transaction lock миграции, применить отсутствующую версию SQL и записать schema_migrations.
2. Проверить `seed_complete`. Если он уже установлен, сохранить весь источник и изменения; повторное чтение официальных файлов не требуется.
3. Если seed отсутствует, прочитать четыре файла отдельным bootstrap-only loader, проверить схемы, ссылки и уникальность завершений.
4. В транзакции с отдельным advisory lock повторно проверить marker, загрузить каталоги/профили/историю, создать demo-аккаунты и установить seed marker.

Marker выставляется последним и коммитится вместе с данными. Ошибка останавливает запуск с ненулевым кодом. Автоматического reset или замены уже загруженного источника нет.

`./data/source` монтируется в `/app/data/source:ro`. Официальные данные, `.env`, локальные зависимости и логи не включаются в Git/образ. База сохраняется в именованном `postgres_data`, путь внутри PostgreSQL 18 — `/var/lib/postgresql`. Приложение слушает 0.0.0.0 внутри контейнера, наружу порты опубликованы на loopback машины.

Конфигурация: `DATABASE_URL`, `DATASET_DIR`, `APP_ORIGIN`, `APP_PORT`, `DB_PORT`, `POSTGRES_PASSWORD`, `DEMO_EMPLOYEE_PASSWORD`, `DEMO_HR_PASSWORD`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_API_URL`; адаптер также читает `LLM_TIMEOUT_MS`. Дефолтный адрес локальной БД для разработки — `127.0.0.1:54329`; внутри Compose приложение обращается к `db:5432`. Внешние аккаунты для БД не нужны.

`docker compose down` сохраняет состояние. Только явное удаление тома, например `docker compose down --volumes`, удаляет данные, импорт, сессии и симуляции. При следующем запуске потребуется исходный набор. Пароли demo-аккаунтов не переписываются при обычном restart существующей БД.

## 15. Проверки и пределы

Подтверждены 21 доменная проверка и 8 интеграционных проверок хранилища; дополнительные HTTP/AI-проверки находятся рядом в `backend/tests`. Актуальный совокупный результат фиксируется командами и отчётом запуска, а не числом в архитектуре.

Проверки хранилища используют явно заданный `TEST_DATABASE_URL` и случайную схему `cq_test_*`. Они создают собственные синтетические данные и удаляют только свою схему. Без test URL набор integration пропускается; рабочее demo не сбрасывается.

Проверено хранение полного официального набора, повторный bootstrap с сохранением состояния, receipt replay до проверки версии, один победитель конкурентной симуляции, запрет чужого профиля, атомарный отказ импорта, add/identical-поведение и защита от двойного начисления через импорт. Доменные проверки покрывают baseline, границы gain/max_level, цели, подготовительные шаги и историю; источник и overlays не начисляются дважды.

Текущие ограничения: одна компания; demo-аккаунты; только симуляции новых выполнений; add-only импорт; один шаг поиска prerequisites; отсутствие кэша AI, очередей и внешних кадровых интеграций; сериализация всех доменных записей общей metadata-строкой. Эти ограничения видны в поведении API и не скрываются фикстурами.

Нагрузочные гарантии, резервное восстановление, работа реального AI-провайдера и его качество относительно baseline требуют отдельных испытаний. Наличие Dockerfile и модульной архитектуры само по себе их не подтверждает.
