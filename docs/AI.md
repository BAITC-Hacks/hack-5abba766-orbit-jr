# AI-зона: реализация и подключение

Модули реализуют ранжирование из разделов 9–10 [BACKEND.md](BACKEND.md).
Общие типы — в [contracts/backend.ts](../contracts/backend.ts).
HTTP, авторизация, построение кандидатов и повторная проверка версии относятся к backend-сервису.

| Файл в `frontend/` | Назначение |
|---|---|
| `src/server/ai/recommend.ts` | Единый вход: AI / объяснимый fallback / отсутствие кандидатов |
| `src/server/ai/adapter.ts` | OpenAI Structured Outputs, отмена, дедлайн, безопасные причины сбоя |
| `src/server/ai/prompt.ts` | Промпт, snapshot одного сотрудника, JSON-схема |
| `src/server/ai/response-validator.ts` | Строгая схема и проверка принадлежности всех ссылок |
| `src/server/domain/baseline.ts` | Многофакторное ранжирование и объяснения fallback |
| `src/server/domain/baseline-signals.ts` | Последние три терминальных исхода того же события |
| `src/server/domain/recommendation-evidence.ts` | Общий инвариант доказательств кандидата |
| `evaluation/cases.ts`, `evaluation/metrics.ts` | Авторские синтетические случаи и метрики |
| `scripts/evaluate-ai.ts` | Offline-проверка и явный запуск живой модели |

## Вызов из backend-сервиса

```ts
const signals = buildBaselineSignals(input.candidates, {
  employeeId,
  asOfDate: input.as_of_date,
  history: sourceHistory,
  unlockedWeightedGain,
})

const result = await recommend(input, {
  signals,
  signal: request.signal,
  ...(input.candidates.length === 0 ? { emptyReason } : {}),
})
```

`signals` обязателен у `recommend`: сервис явно передаёт рассчитанные значения.
Обе карты индексируются по **candidate_id**, не по event_id. Один event может иметь разные попытки.
`unlockedWeightedGain` поступает из EligibilityEngine: максимальная польза одного
реально открываемого следующего события, без суммы альтернатив. Из одних
`unlocks_event_ids` эту величину вычислить нельзя. Нужны каталог и расчёт допуска.

`buildBaselineSignals` использует только исходные записи нужного сотрудника
до `as_of_date` включительно. Для каждого события берёт три последних исхода
`completed / declined / dropped / no_show`; отрицательные среди них —
`declined / dropped / no_show`. `in_progress` и `overdue` не являются завершённым
исходом и здесь не учитываются. При равной дате порядок стабилизируется record_id:
более точного времени в контракте нет. Отсутствие истории даёт нулевой штраф;
EvidenceBuilder отдельно описывает отсутствие данных, без вывода о мотивации.

Сервису остаётся:

1. Проверить сессию, права, runtime-схему входа и expected_version.
2. Построить допустимых кандидатов, факты, сигналы и DomainVersion из одного снимка.
3. Закрыть read-транзакцию перед ожиданием модели.
4. Ограничить параллельные запросы на одного сотрудника/версию.
5. Вызвать `recommend` и **повторно проверить версию** перед выдачей любого результата.
   При изменении вернуть `409 STALE_RECOMMENDATION`, включая случай fallback.
6. Преобразовать результат в общий API-конверт. Не показывать traceback пользователю.

Эти операции не выполнены внутри `recommend`: модуль не читает и не меняет БД.

## Допустимое объяснение

- Каждый кандидат заранее имеет непустые уникальные fact_id и непустой текст фактов.
- Есть минимум три разные категории из `grade / skill_gap / history / target_requirement`.
  `eligibility` и `effort` дополняют объяснение, но не заменяют эти три категории.
- Проверяются **все** кандидаты до обращения к модели, включая не вошедших в baseline top-N.
- Некорректный серверный snapshot вызывает исключение. Его нельзя маскировать успешным fallback:
  сервис должен исправить evidence и вернуть обычную серверную ошибку.
- Модель возвращает только ID. Неизвестные поля, собственные числа/текст, неизвестные
  кандидаты, чужие факты, дубли, слишком длинный список и неверная альтернатива отклоняются.
- Карточка собирается из серверного Candidate с исходной participation_id/session_date.
  Модель не может подменить прирост, событие, попытку или описание.
- Fallback сохраняет все факты по порядку категорий. Факт условной пользы prerequisite
  не теряется, если в той же категории уже был факт о цели.

Это обеспечивает принадлежность ссылок и полноту категорий. **Истинность текста
обеспечивает EvidenceBuilder; валидатор не доказывает причинную релевантность выбора.**
Три корректные ссылки могут сопровождать слабую рекомендацию — это отдельная проверка качества.

## Baseline: порядок сравнения

1. Число полностью закрытых критических разрывов.
2. Взвешенное сокращение оставшегося разрыва до цели + `0.5 × unlockedWeightedGain`.
   Вес критического навыка 2, прочих 1. Не относящийся к цели рост и рост выше
   требования не повышают этот балл. Фактический прирост в карточке сохраняется.
3. Меньше отрицательных исходов среди последних трёх терминальных участий события.
4. Меньше часов.
5. При полном равенстве — continue, затем event_id и candidate_id.

Будущая польза подготовительного события остаётся условной: она не записывается
в текущие навыки. Эффекты 1–3 альтернативных карточек нельзя складывать.
Это прозрачная продуктовая эвристика, не обученная вероятность успеха.
Модель получает задачу учитывать цель и историю, выбирать полезные шаги и ссылаться
на определяющие выбор факты. Её добавочную пользу нужно измерять отдельно.

## Режимы и бюджет времени

| Условие | Результат |
|---|---|
| Валидный ответ модели | `mode: ai` |
| Нет ключа | `rules_fallback`, `missing_api_key` |
| Истёк бюджет провайдера | `rules_fallback`, `provider_timeout` |
| Сбой провайдера или отмена caller signal | `rules_fallback`, `provider_error` |
| Отказ, обрезанный/пустой/невалидный ответ | `rules_fallback`, `invalid_response` |
| Нет кандидатов, сервис передал emptyReason | `no_candidates`, модель не вызывается |
| Некорректный snapshot / потеря причины пустого набора | Исключение, исправить backend-вход |

По умолчанию провайдеру даётся 8000 мс. Настройка может уменьшить бюджет;
значение выше 8000 ограничивается. Некорректная строка возвращает значение по умолчанию.
Повторные запросы SDK отключены. Независимый дедлайн завершает ожидание даже если
транспорт игнорирует AbortSignal; слушатель и таймер очищаются после ответа.
Сырые ошибки SDK и ключи не попадают в detail. `isAiConfigured()` проверяет наличие
ключа, а не доступность провайдера.

8 секунд — ограничение ожидания адаптера. Целевые 10 секунд на HTTP целиком
требуют измерения построения snapshot и работы сервиса; этот результат пока не получен.

## Конфигурация и команды

Локальный файл: `frontend/.env.local`, исключён из Git. Значения серверные,
без `NEXT_PUBLIC_`:

```dotenv
LLM_API_KEY=replace_locally
LLM_MODEL=gpt-4o-mini
LLM_TIMEOUT_MS=8000
```

Текущее значение модели сохранено из предыдущей реализации. Выбор модели и её
доступность аккаунту подтверждаются живым вызовом, не предположением.
Адаптер рассчитан на OpenAI Chat Completions с json_schema; произвольная подстановка
модели другого семейства не гарантирует совместимость всех параметров.
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
обеспечивает форму ответа; семантическая проверка ID остаётся нашей обязанностью.

Все команды из `frontend/`:

```sh
npm ci
npm test
npm run typecheck
npm run build
npm run eval:ai
npm run eval:ai -- --json
npm run smoke:ai
npm run eval:ai -- --live --json
```

`eval:ai` без `--live` всегда работает локально, даже при наличии ключа.
`smoke:ai` делает один платный запрос; `--live` — по одному на каждый из семи случаев.
Оба живых режима требуют настроенного ключа. Скрипт читает .env.local загрузчиком Next.
Официальные данные скрипт не загружает: используются только самостоятельно придуманные случаи.

## Что измеряет evaluation

Семь сценариев: критический разрыв против минимального навыка; история при равной
пользе; нерелевантный прирост; рост выше требования; prerequisite с нулевым прямым
прогрессом; продолжение конкретной попытки; произвольные новые ID.

Отчёт содержит фактический top-1, baseline top-1, прохождение авторского ожидания,
валидность ссылок, время, размер пользовательского payload и причину fallback.
Размер payload не включает system-промпт и JSON-схему. Время CLI не является HTTP-латентностью.

Метрики AI считаются только для принятых ответов режима `ai`. Fallback не засчитывается
ни как успешный AI-выбор, ни как согласие модели с baseline. Поэтому читать
`aiExpectedChoicePassRate` нужно **вместе** с `aiAcceptanceRate` и `fallbackRate`.
В offline-отчёте AI-метрики равны null — они не измерены.

Код выхода 1: baseline нарушает ожидание/ссылки; в live также нет принятого ответа AI,
неверен ожидаемый выбор или время случая превысило 10 секунд. Успешный fallback не делает
живой прогон успешным. Авторские ожидания проверяют регрессии, не скрытые тесты жюри.

## Границы текущей проверки

Нет подтверждённого live-прогона, HTTP-интеграции, замеров полного каталога,
независимого holdout или экспертной разметки. Семь сценариев созданы вместе с правилами,
поэтому прохождение 7/7 не доказывает обобщение и превосходство AI.
Следующий эксперимент: зафиксировать отдельный набор до правок промпта, затем сравнить
минимальный навык, этот baseline и AI, разобрать каждое расхождение и показать latency/fallback.
План приоритетов — [AI_PLAN.md](AI_PLAN.md).
