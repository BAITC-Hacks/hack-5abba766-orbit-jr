# AI-зона Career Quest

AI-реализация команды, включая проверки фактов и evaluation из `9b577ec`, перенесена в серверный workspace и интегрирована с доменным ядром. **В приложении один адаптер провайдера и одна реализация baseline.** Прежние исполняемые модули и AI-тесты из `frontend/src/server` и `frontend/tests` перенесены в `backend/`.

| Файл | Ответственность |
|---|---|
| `backend/src/ai/prompt.ts` | Промпт команды, компактный snapshot и JSON Schema |
| `backend/src/ai/adapter.ts` | HTTP-транспорт провайдера, общий timeout, один ограниченный повтор и типизированные причины отказа |
| `backend/src/ai/response-validator.ts` | Строгая Zod-схема, проверка ID/фактов и сборка карточек |
| `backend/src/ai/recommend.ts` | Общий подбор AI/fallback для сервиса и evaluation |
| `backend/src/ai/index.ts` | Совместимые функции ранжирования и проверки |
| `backend/src/domain/baseline.ts` | Единый детерминированный comparator и выбор фактов fallback |
| `backend/src/domain/baseline-signals.ts` | Негативные исходы последних терминальных попыток |

## Вызов

Recommendation service получает допустимых кандидатов и три карты сигналов из доменного ядра, затем вызывает:

```ts
const result = await recommend(input, { signals, signal })
```

`recommend` готовит проверенный baseline, передаёт три карты сигналов в `rankWithModel(input, signal, signals)` и проверяет ответ. Транспорт возвращает `AdapterResult`, не бросая сетевые ошибки. Ошибки провайдера возвращают `rules_fallback` с причиной `missing_api_key`, `provider_timeout`, `provider_error` или `invalid_response`. Неполные или противоречивые серверные факты считаются ошибкой построения snapshot; они не превращаются в правдоподобное объяснение.

Пустой набор обрабатывается до адаптера как `no_candidates`; причину определяет домен. Fallback использует тот же comparator и полные сигналы истории и будущей пользы, что и доменное ядро.

В пределах общего `LLM_TIMEOUT_MS` (не более 8000 мс) адаптер делает максимум две попытки. Сетевой сбой или HTTP 408/429/500/502/503/504 допускают один повтор с задержкой не менее 250 мс. `Retry-After` учитывается как секунды либо HTTP-дата; после задержки должно оставаться не менее 2000 мс бюджета, иначе сразу возвращается fallback. Ошибки авторизации, невалидный JSON и отказ модели не повторяются. Отмена вызывающего запроса прерывает транспорт и ожидание повтора. Незавершённое тело HTTP-ошибки закрывается до повтора, общий таймаут не запускается заново.

Сервис проверяет версию до вызова и после ответа. PostgreSQL advisory lock ограничивает параллельный подбор одной employee/version; во время HTTP-вызова транзакция БД не удерживается. Изменившийся снимок отклоняется как `STALE_RECOMMENDATION`.

На один процесс допускается не более трёх подборов; лишний отдельный запрос получает HTTP 429 `RECOMMENDATION_BUSY`. Одинаковые выполняющиеся вызовы без `AbortSignal` объединяются. HTTP-запросы с сигналом выполняются независимо, чтобы отмена одного не прервала чужую работу; одновременный подбор той же employee/version защищён PostgreSQL lock. Успешные AI-ответы кэшируются на 60 секунд, максимум 128 записей; fallback и ошибки не кэшируются. Перед поиском в кэше читается свежий снимок и проверяется ожидаемая версия. Ключ-хэш учитывает сотрудника, вход, числовые сигналы, лимит, промпт, схему и конфигурацию провайдера. Подробности и ограничения — [Качество рекомендаций](RECOMMENDATION-QUALITY.md).

Блокировки используют отдельный `recommendationLockPool` на 10 соединений, чтобы ожидающий AI не
занимал обычный пул профиля/HR. Очередь подключения ограничена 1 секундой;
переполнение даёт `503 STORAGE_BUSY`. Конфигурационный предел двух пулов — 20
соединений PostgreSQL: 10 обычных и 10 для AI-блокировок; лимит работы сервиса остаётся 3. HTTP передаёт `request.signal` до адаптера: отмена прерывает транспорт. Адаптер ограничивает чтение тела тем же дедлайном и прерывает транспорт при ошибочном HTTP-статусе. Освобождение advisory lock выполняется в `finally`; `closePools()` закрывает оба пула.

Размер ответа провайдера ограничен 64 КиБ декодированных транспортных байтов.
Чтение проверяет UTF-8 и требует одну completion с `finish_reason: "stop"`.
Превышение размера или повреждённый ответ приводит к `invalid_response` fallback;
при отмене или ошибке незавершённый поток закрывается.

## Ground truth и проверки ответа

Промпт сохраняет подход команды: модель выбирает существующие candidate ID и факты, предпочитает закрытие критических разрывов, учитывает начатые активности и подготовительные шаги. Добавлено явное правило: карточки — альтернативы из одного состояния; будущие эффекты открываемого события ещё не получены.

В prompt попадают роль/грейд, цель, навыки и компактные кандидаты с проверенными фактами. ФИО, руководитель, свободные исходные описания и чужие профили не передаются. Текст payload обозначен как данные, а не инструкции.

История содержит отдельные сводки похожих добровольных активностей с тем же и другим форматом за предшествующий год: до шести итоговых наблюдений на группу, с числителем, знаменателем и оговоркой при выборке меньше трёх. Для подготовительных шагов добавлены серверные числовые факты о будущем эффекте следующей активности. Этот эффект остаётся условным и не прибавляется к текущему прогрессу.

Валидатор отклоняет:

- Неизвестные/повторные кандидаты, пустой список и больше `min(limit, количество кандидатов)` выборов.
- Факты другого кандидата, неизвестные и повторные ID фактов.
- Меньше трёх категорий из `grade`, `skill_gap`, `history`, `target_requirement`.
- Неизвестную альтернативу или альтернативу, уже входящую в выбранные рекомендации.
- Лишние поля, включая свободные объяснения и числовые обещания модели.

Карточки собираются исключительно из исходных серверных Candidate. Provider null в поле альтернативы нормализуется в соответствие с общими TypeScript-типами.

Перед строгой проверкой ответа провайдера `validateProviderRanking` отбрасывает только необязательное сравнение, ссылающееся на уже выбранную карточку (в том числе на саму себя). Luna иногда строит такую цепочку при правильном основном ранжировании. Порядок, выбранные ID и факты не изменяются; корректные невыбранные альтернативы сохраняются. Неизвестные ID, неверные факты и лишние поля по-прежнему приводят к fallback. Режим `ai` означает проверенный выбор модели; необязательное сравнение могло быть отброшено. Исходный ответ не считается целиком корректным, а отображаемые карточки проходят неизменённый строгий валидатор.

## Полный baseline

Comparator из командного `baseline.ts` встроен в `getCandidates` вместо прежней локальной сортировки. В нём исправлен расчёт прямой пользы:

```text
closed_gap = max(0, min(after, required) - min(before, required))
weighted_direct_gain = sum(closed_gap × (critical ? 2 : 1))
```

Навык вне целевых требований и рост сверх нужного уровня не увеличивают карьерную полезность.

Доменный код обязательно передаёт для **каждого** кандидата:

- `unlockedWeightedGain`: максимальную взвешенную пользу одного следующего открываемого события, рассчитанную после эффекта текущего шага;
- `negativeOutcomes`: число негативных исходов среди последних трёх терминальных попыток того же события;
- `similarFormatPenalty`: долю негативных исходов других активностей с общим развиваемым навыком и тем же форматом за год, среди максимум шести последних итоговых наблюдений. При выборке меньше трёх значение равно нулю; это не вероятность завершения.

Отсутствие сигнала считается ошибкой программирования. В production нет опционального default, который незаметно превращает полное ранжирование в упрощённое.

Порядок: закрытые критические разрывы → прямая польза + 0,5 × открываемая польза → меньше негативных исходов той же активности → меньший штраф похожего формата → меньшая длительность → предпочтение продолжения при равенстве → event ID → candidate ID. Карточки fallback используют проверенные факты и не выдумывают альтернатив.

## Конфигурация

- Текущая модель в `.env.example` — `gpt-6-luna`. Для существующего запуска также обновите `LLM_MODEL` в локальном `.env` и перезапустите приложение; для Docker выполните `docker compose up -d --build --force-recreate app`, чтобы обновились и окружение, и код. Ключ в `.env.example` остаётся пустым.
- `LLM_API_KEY` и `LLM_MODEL` — оба обязательны для AI-режима. Непроверенного дефолта модели больше нет.
- `LLM_API_URL` — полный серверный URL Chat Completions; по умолчанию `https://api.openai.com/v1/chat/completions`.
- `LLM_TIMEOUT_MS` — по умолчанию 8000; фактический диапазон 100–8000 мс.

Финальная проверка Luna 2026-09-23: `--live --suite=all --repeat=3` — 69/69 вызовов на 23 авторских сценариях прошли все проверки, без fallback; обе проверки пустого состояния также прошли. p50 вызова рекомендации — 2,487 с, p95 — 3,986 с, максимум — 6,783 с (без HTTP, БД и браузера). `verify:ai-flow -- --live` — 3/3 интеграционных теста на отдельной временной PostgreSQL БД, включая два настоящих ответа Luna после изменения навыков. Unit-тесты и production-сборка прошли. Ранее на том же наборе были 66/69, затем 67/69 полных прохождений: исправлены необязательные сравнения, подсчёт разных категорий и ссылки на решающую историю. [Полный отчёт](ORCHESTRATION_VERIFICATION.md) сохраняет все три прогона. Это авторская регрессия, а не независимый holdout, гарантия безошибочности модели или проверка браузерного пути. Исходные отчёты Sol ниже относятся к прежней модели.

Используется один fetch-запрос без автоматических retries, с `store:false`, ограничением `max_completion_tokens=1400` и JSON Schema. Endpoint задаётся только серверным окружением; HTTP-пользователь изменить его не может. Внешний AbortSignal также поддерживается. Ключ не является `NEXT_PUBLIC_*`.

`isAiConfigured()` проверяет наличие непустых key/model и не обращается к провайдеру. Транспорт не возвращает наружу содержимое ошибки провайдера или секреты.

## Проверки

```sh
npm run typecheck -w backend
npm run test -w backend
npm run eval:ai
```

Командные тесты перенесены в `backend/tests/team-ai/` и `backend/tests/team-baseline.test.ts`. SDK-моки заменены контролируемым fetch; сохранены проверки структуры, фактов, альтернатив и comparator. Добавлены регрессии на прирост вне цели/сверх требования, обязательные сигналы, таймаут, явную модель, лишний model prose и повторные факты. Существующие проверки recommendation service на revisions и освобождение DB-соединения также сохраняются.

`npm run eval:ai` запускает авторские синтетические сценарии из `backend/evaluation/` без вызовов провайдера, даже если ключ настроен. Проверяются конкуренция критического и самого слабого навыка, история отказов, прирост вне цели и сверх требования, подготовительный шаг, продолжение и новые непривычные ID.

Отдельные доменные сценарии проходят через реальные схемы исходных профилей/истории, проверку связей и `getCandidates`. `domain-evaluation.test.ts` пропускает эти входы через настоящий адаптер с контролируемым fetch и сверяет обещанный эффект с доменной симуляцией завершения. Дополнительно проверяются пустые наборы кандидатов. Отчёт CLI содержит p50/p95 времени ранжирования; HTTP, БД и браузер в этот замер не входят.

Для живой проверки задайте `LLM_API_KEY` и `LLM_MODEL` в корневом `.env`:

```sh
npm run smoke:ai
npm run eval:ai -- --live
```

Эти команды отправляют только авторские синтетические примеры. Отчёт разделяет baseline, принятые AI-ответы и fallback: fallback не засчитывается как совпадение AI с baseline. Измеряются ожидаемый первый выбор, корректность ссылок на факты, размер payload, задержка и режим ответа. Отсутствующие измерения AI в offline-режиме обозначены `null`. Совпадение с авторским ожидаемым ответом не является доказательством пользы продукта или качества на скрытых профилях жюри.

PostgreSQL/HTTP integration запускается отдельно; актуальные результаты общего набора фиксируются командами проверки проекта.

Командные живые проверки и их ограничения записаны в [AI_VERIFICATION.md](AI_VERIFICATION.md): для сохранённой там конфигурации GPT-6 Sol прошли 51/51 авторских проверок. Это отчёт конкретного upstream-прогона на самостоятельно созданных данных, а не подтверждение AI-режима текущего локального запуска; наличие key/model проверяется отдельно. Совпадение с baseline не доказывает дополнительную пользу LLM: промпт задаёт ту же эвристику, а реальные кандидаты уже поступают отсортированными доменным ядром.

## Факты и числовой контекст

Модель получает `ranking_factors`, рассчитанные общей функцией `candidateRankingFactors`, которую использует и baseline: число закрытых критических разрывов, полезный прямой прирост, лучшую условную будущую пользу, число негативных терминальных исходов и штраф похожего формата. Production-вызов `recommend` требует полные сигналы, включая явные нули; пропущенные значения не подменяются нулями. Совместимый низкоуровневый вызов без сигналов не добавляет числовой контекст.

Факт истории и сигнал ранжирования используют общий отбор последних трёх терминальных исходов того же сотрудника и события до даты среза. Текущая незавершённая попытка описывается отдельно. Для каждого открываемого события домен добавляет отдельный факт с его ID, будущими уровнями после подготовки и условным целевым эффектом. Эти эффекты не начисляются заранее и не суммируются между альтернативами.

Для `gpt-6-sol` и `gpt-6-luna` адаптер задаёт `reasoning_effort: low` без `temperature`; для GPT-4o/4.1 — `temperature: 0`. Остальные модели требуют отдельной проверки совместимости. Настройки следуют [документации GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna) и [правилам параметров](https://developers.openai.com/api/docs/guides/latest-model). Корневой `.env.example` указывает выбранную модель; доступность определяется аккаунтом и живым вызовом.

### Проверка надёжности 23 сентября 2026

После переключения на `low` выполнен [новый живой прогон](verification/2026-09-23-ai-reliability.json): 23 из 23 авторских сценариев получили принятый AI-ответ, все проверки выбора, фактов и размеченного порядка прошли. Этот прогон проверял настройку `low` до добавления транспортного повтора; метрики не включают HTTP и БД.

Затем добавлен один ограниченный повтор. Через HTTP на `localhost:3000` проверен существующий профиль сотрудника с лимитами 1, 2 и 3: все три свежих подбора вернули `mode: ai` за 2,11 / 4,41 / 3,56 с, повтор последнего запроса — за 56 мс из кэша. Версия профиля до и после не изменилась. Это наблюдения конкретного прогона, а не гарантия доступности внешнего API.

## Расширенная оценка и сквозной сценарий

```sh
npm run eval:ai -- --suite=all
npm run eval:ai -- --suite=domain
npm run eval:ai -- --live --suite=comparison --repeat=3
npm run eval:ai -- --live --suite=acceptance --repeat=3
npm run verify:ai-flow
npm run verify:ai-flow -- --live
```

По умолчанию запускается `regression`: 7 исходных случаев. `challenge` содержит 8 конфликтных случаев, `acceptance` — 2 дополнительных, `domain` — 6 случаев через доменный расчёт и 2 отдельные проверки пустого результата. `comparison` объединяет первые два набора (15), `all` — все 23 случая ранжирования плюс проверки пустых состояний. Исторический живой отчёт на 17 случаях предшествует включению `domain`. `--repeat=1..5` повторяет каждый случай ранжирования. Live-команды расходуют API; offline не вызывает провайдера даже с настроенным ключом.

Проверяются первый выбор, принадлежность фактов, версия snapshot и явно размеченные решающие факты. В multi-card acceptance проверяется весь выданный префикс ожидаемого порядка (от одной до трёх карточек). Для остальных случаев отсутствие разметки порядка отмечено `null`. Ошибка выбора, решающего факта, порядка, fallback или превышение 10 секунд делает live CLI неуспешным. `aiEndToEndPassRate` здесь означает прохождение проверок границы `recommend`, а не браузерного сценария.

JSON-отчёт сохраняет модель, время, p50/p95/max, выбранные ID, причины fallback и SHA-256 промпта, схемы и случаев. Для чистого JSON без заголовков npm можно выполнить из корня:

```sh
node --import tsx --env-file=.env backend/scripts/evaluate-ai.ts --live --suite=all --repeat=3 --json
```

`verify:ai-flow` требует `TEST_DATABASE_URL`, создаёт временную PostgreSQL-схему и удаляет только её. Проверяется авторизованный HTTP Request/Response handler, настоящий PostgreSQL, изменение навыков и рекомендаций после completion, идемпотентность, HR и импорт новых ID. По умолчанию провайдер не вызывается; `--live` добавляет два настоящих запроса до и после выполнения. Управляемая гонка использует локальный HTTP mock провайдера и явно отмечена в отчёте. Браузер и TCP-сервер Next в этот runner не входят. Отчёт: `test-results/ai-flow.json`.
