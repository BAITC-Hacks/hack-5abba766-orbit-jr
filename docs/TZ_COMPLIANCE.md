Затем поступили ещё 12 commit до `d4b1670`: новые guards AI, ограничения ожиданий PostgreSQL и уточнения интерфейса. Они также подтянуты fast-forward с сохранением редакции README; основные команды проверки повторены. Итоговый проверяемый код — `d4b1670`. README переработан отдельно после проверки кода.

На новых импортированных профилях жюри может проверить данные и рекомендации через HR. Импорт не создаёт аккаунт сотрудника; HR не может проходить активность за него. Полный цикл самостоятельного выполнения демонстрируется через существующий employee-аккаунт или отдельную авторскую репетицию. Это ограничение аккаунтов необходимо учитывать при показе.

| Ограничения источников | Исходные файлы и ключи исключены из Git; расширять данные можно при сохранении схемы. В опубликованных live-сценариях используются авторские данные |

## Ограничения и нефункциональные требования ТЗ

| Требование | Статус и граница |
|---|---|
| Не выдавать однофакторное правило за AI | Соблюдается: есть реальный LLM-адаптер; многофакторный резервный подбор явно помечен `rules_fallback` |
| Нет публичных рейтингов результативности | Соблюдается в текущем интерфейсе; поиск и HR-списки не представлены как рейтинги |
| Нет наград за обязательные процессы | Обязательные активности исключаются из добровольных рекомендаций и моделирования выполнения; системы наград нет |
| Синтетические данные, отсутствие реальных персональных данных | Используется предоставленный синтетический набор; дополнительные проверочные данные авторские |
| Приватность внутреннего контура | Сотрудник получает доступ только к собственному профилю. HR видит компанию. Ключ API хранится на сервере; ФИО и полная история компании не отправляются в модель |
| Разграничение employee / HR | Проверяется сервером: HR может читать и импортировать, но не менять цель и не проходить обучение за сотрудника |
| Добровольность | Пользователь выбирает цель и действие, обязательные процессы не становятся предметом стимулирования |
| Explainability | Видны исходные факты, числовой эффект и способ расчёта покрытия; 100% не обещает повышение |
| Запуск одной командой | `docker compose up --build -d --wait` после подготовки `.env` и четырёх исходных файлов. Репетиция без архива запускается отдельным документированным способом |
| UI ≤2 секунды | Полностью не подтверждено. В [предыдущем браузерном проходе](JURY_VERIFICATION.md) один запрос профиля занял 2 811 мс. Причина не изолирована; успешные тесты и свежий health не доказывают SLA |
| AI ≤10 секунд | На `d4b1670` два live-запроса на границе HTTP handlers с PostgreSQL: 2929 и 2002 мс. Это отдельные наблюдения, без браузера и TCP Next. Бюджет провайдера 8 секунд не ограничивает весь путь; SLA под нагрузкой не подтверждён |

Внешний провайдер технически отключаем, однако AI является обязательным требованием кейса. Поэтому работоспособный резервный подбор и `ai_configured=true` не заменяют демонстрацию принятого `mode=ai`.

Последнее объединение дополнительно проверяет порядок AI-карточек против общей с baseline политики: критические разрывы → суммарная условная польза → история активности → история похожего формата → длительность → продолжение. Нарушение отклоняет весь ответ в `rules_fallback / invalid_response`; сервер не исправляет порядок под меткой AI. Совпадение принятых ответов с правилами теперь является условием допуска, а не независимой метрикой преимущества модели. В [аудите ML/AI](ASTRA_ML_AUDIT.md) сохранены и неуспешные live-gates: 50/54 AI в стресс-серии и 22/23 в основном наборе на предшествующей версии.

Ожидания SQL ограничены и преобразуются в `503 STORAGE_BUSY`; отмена после inference освобождает AI-соединение и блокировку. Это не доказывает суммарный SLA. Известный дефект клавиатурной навигации — skip-link/hash может сбросить фокус и локальный раздел — описан в [аудите интерфейса](../AUDIT-2026-09-23.md). Его воспроизведение относится к `609ebc3`, а затронутый обработчик сохранён в `d4b1670`; новая проверка этого дефекта здесь не выполнялась.
