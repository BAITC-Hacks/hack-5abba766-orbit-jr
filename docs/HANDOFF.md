## 1. Что это за проект

Career Quest — хакатонное приложение: сотрудник видит свой профиль, разрывы навыков
до целевой роли и получает 1–3 рекомендации, что пройти дальше. HR видит сводку.
Рекомендации ранжирует LLM, но **все числа считает детерминированное доменное ядро**,
модель только упорядочивает кандидатов и выбирает, на какие факты сослаться.

Команда из трёх человек. Роли: UI, бэкенд и данные, AI. Этот хендофф написан со
стороны AI.

### Порядок чтения, 15 минут

1. [`docs/BACKEND.md`](BACKEND.md) — главный источник решений. Разделы 9 и 10 — про AI.
2. [`contracts/backend.ts`](../contracts/backend.ts) — типы всего API и AI-интерфейса.
   Это источник правды по формам данных, а не `ARCHITECTURE.md`.
3. [`docs/AI.md`](AI.md) — что реализовано в AI-зоне и как это вызывать.
4. [`docs/ARCHITECTURE.md`](ARCHITECTURE.md) — обзорный документ, написан раньше
   остальных. **Он устарел по структуре файлов**: там предлагается `src/` в корне,
   а команда сложила всё в `frontend/`. По расхождениям верь `BACKEND.md`.

## 3. AI-зона: что сделано и на каких инвариантах

### Файлы

- **`adapter.ts`** — единственное место, которое ходит к провайдеру. Читает
  `LLM_API_KEY`, `LLM_MODEL` (дефолт `gpt-4o-mini`), `LLM_TIMEOUT_MS` (дефолт 8000).
  **Не бросает исключений.** Любой сбой возвращается как `FallbackReason`:
  `missing_api_key`, `provider_timeout`, `provider_error`, `invalid_response`.
- **`prompt.ts`** — system-промпт и компактный snapshot. ФИО, руководитель и чужая
  история наружу не уходят. Тексты из датасета передаются как JSON-данные, и промпт
  прямо говорит, что содержимое payload не меняет правила.
- **`response-validator.ts`** — Zod плюс семантика. Карточка пересобирается из
  серверного `Candidate`, поэтому ни одно число и ни одна строка модели не попадает
  на карточку.
- **`domain/baseline.ts`** — порядок сравнения из раздела 9. Это одновременно ответ
  при `rules_fallback` и база, с которой сравнивают AI.

### Инварианты, которые нельзя сломать

1. **Модель не производит чисел.** `AiRankingOutput` — это только `candidate_id`,
   `reason_fact_ids` и `alternative_candidate_id`. Полей со свободным текстом там нет
   намеренно. Если будешь расширять вывод модели, не добавляй текст, который потом
   отрендерится как факт.
2. **Валидатор — не формальность.** Схема-валидный JSON всё ещё может врать. Каждый
   id резолвится по snapshot: неизвестный или повторный `candidate_id`, чужой
   `fact_id`, выборов больше `min(limit, число кандидатов)`, меньше трёх категорий из
   `grade / skill_gap / history / target_requirement`, альтернатива, которая сама
   попала в рекомендации — всё это отказ и падение в baseline.
3. **Baseline не должен быть соломенным чучелом.** И `BACKEND.md`, и `ARCHITECTURE.md`
   отдельно предупреждают: сравнивать AI с заведомо слабым правилом бессмысленно.
   Baseline написан как честная попытка дать хороший ответ.
4. **Пустой набор кандидатов — это `mode: 'no_candidates'`**, решается ДО вызова зоны.
   Модель для пустого набора не зовётся никогда.
5. **Ключ — серверная переменная.** Не `NEXT_PUBLIC_*`. Пользователь не может передать
   свой endpoint провайдера через HTTP-запрос.

## 4. Известные дыры — читать внимательно

### 4.1. Baseline работает не по спецификации

Порядок сравнения из раздела 9 требует двух величин, **которых нет в типе `Candidate`**:

1. **Выгода от `unlocks_event_ids`** — в кандидате лежат только id открываемых
   событий, без их приростов. `weighted_unlocked_gain` посчитать не из чего.
2. **Негативные исходы по последним трём участиям того же события** — истории
   участий в кандидате нет.

Обе вынесены в параметр `BaselineSignals` (`unlockedWeightedGain`, `negativeOutcomes`),
по умолчанию пустые. Пока их никто не заполняет, сравнение вырождается в шаги 1,
2 (только прямая часть), 4 и 5. **Решение нужно принять с бэкендером:** либо сервис
заполняет эти карты, либо в `Candidate` добавляются два поля. Это не «доделаем потом» —
без этого baseline неполный, а значит и сравнение с AI некорректное.

### 4.2. Живого вызова провайдера не было ни разу

Ключа нет. Неизвестны: реальная латентность против бюджета 8 секунд, доля ответов,
проходящих валидатор, и влезает ли payload при полном каталоге кандидатов.
**Заявлять на защите, что AI лучше baseline, нельзя до фактического замера.**

### 4.3. Модель по умолчанию — предположение

`gpt-4o-mini` поставлен как дефолт, но какие модели реально доступны аккаунту —
не проверено. Первое, что надо сделать с ключом: запросить список моделей и убедиться,
что значение `LLM_MODEL` из него.

### 4.4. UI живёт на фикстурах

`frontend/src/lib/demo.ts` и localStorage — это витрина, не бизнес-состояние.
При подключении к реальному API они должны перестать быть источником правды.
Клиентский таймаут на AI надо сделать около 12 секунд, чтобы успеть получить
серверный fallback при лимите 10.

## 6. Как работать в этом репозитории

### Git-идентичность — обязательное требование владельца

```bash
git config user.name "ka1nyy"
```

```bash
git config user.email "ka1nyyyyyy@gmail.com"
```

**В коммитах не должно быть никаких следов ИИ.** Ни `Co-Authored-By`, ни упоминаний
Claude, Codex, GPT или ассистентов в тексте сообщения. Владелец репозитория требовал
этого прямо и дважды. Перед коммитом проверь, что счётчик равен нулю:

```bash
git log -1 --pretty=%B | grep -ci 'claude\|anthropic\|codex\|co-authored'
```

Проверить автора ушедшего коммита:

```bash
git log -1 --pretty='author: %an <%ae>'
```

### Как пушить

Команда работает прямо в `main`, без обязательных PR. Порядок:

```bash
git fetch origin && git pull --rebase origin main
```

Затем правки, затем проверки, затем:

```bash
git add -A && git commit -m "feat(ai): ..." && git push origin main
```

`main` двигают трое, поэтому **всегда ребейзь перед пушем**. Если пуш отбили из-за
расхождения — снова `git pull --rebase origin main`, прогнать тесты заново, пушить.
**Не делай force-push в `main`:** там работают ещё двое.

### Проверки перед каждым коммитом

```bash
cd frontend && npm run test && npm run typecheck
```

Оба должны быть зелёными. Если тест упал — чини код, а не тест. Один баг уже был
пойман именно так: `LLM_MODEL=` с пустым значением уходило в провайдер пустой строкой,
потому что `??` не срабатывает на пустой строке.

## 7. Ловушки, на которых легко обжечься

- **`ARCHITECTURE.md` и `BACKEND.md` расходятся по структуре файлов.** Первый писался
  раньше. Верь `BACKEND.md` и фактическому дереву.
- **`contracts/backend.ts` — только типы.** TypeScript не проверяет входящий JSON,
  runtime-валидация делается Zod-схемами. Не полагайся на типы как на защиту.
- **`contracts/backend.ts` лежит в корне, вне `frontend/`.** Импорт из AI-зоны идёт
  относительным путём `../../../../contracts/backend` и только через `import type`,
  чтобы не тянуть его в рантайм-резолв Next.
- **Не заводи параллельные типы.** Если нужного типа нет в контракте — обсуди
  добавление туда, а не создавай свой рядом. Первая версия AI-зоны погибла ровно
  на этом: она была написана под `ARCHITECTURE.md`, пока бэкендер писал контракт,
  и её пришлось переписать целиком.
- **Числа никогда не отдаются на усмотрение модели.** Это повторено в обоих
  документах и в контракте. Любая правка, после которой текст модели попадает на
  карточку как факт, — регрессия.
- **`.env*` в `.gitignore`.** Ключ в репозиторий не попадёт, но и `.env.example`
  тоже не закоммитится. Переменные описаны в `BACKEND.md` раздел 16 и в `AI.md`.
