# Передача работы: Career Quest, AI-зона

Обновлено после интеграции командных изменений 23 сентября 2026. Проект использует
корневой npm workspace с пакетами `backend/` и `frontend/`, PostgreSQL и Docker Compose.
Предыдущая AI-разработка велась в Windows checkout поверх `15c0080`; её код и тесты
перенесены в `backend/`. Команды ниже выполняются из корня репозитория.

## Выбранный кейс и источники

Кейс партнёра **Halyk Bank — Career Quest** на HackAlem AI:
профиль сотрудника → 1–3 обоснованных шага развития → выполнение → новые навыки
и траектория → HR-срез. В ТЗ геймификация вторична; основа — качество рекомендаций.

Прочитать:

1. [BACKEND.md](BACKEND.md) — доменные правила, интеграция и ограничения.
2. [contracts/backend.ts](../contracts/backend.ts) — единые типы API и AI.
3. [AI.md](AI.md) — реализованный интерфейс, конфигурация, ошибки и evaluation.
4. [AI_PLAN.md](AI_PLAN.md) — разбор ТЗ, контраргументы и следующие шаги.
5. [ARCHITECTURE.md](ARCHITECTURE.md), [frontend/README.md](../frontend/README.md) — обзор и клиент.

При расхождениях сверять ТЗ, актуальный контракт и фактический код. Старые
счётчики тестов и сообщения коммитов не являются текущим статусом.

## Что уже есть

- Frontend подключён к относительным `/api` по общему контракту; обработаны версии,
  ошибки, loading/fallback, завершение, импорт, HR. Витрина на фикстурах отделена в `/demo`.
- AI-модуль: `recommend(input, { signals, signal, emptyReason })`, адаптер, промпт,
  строгий валидатор, многофакторный baseline, проверка evidence, расчёт истории.
- Бюджет ожидания провайдера до 8 секунд, отключённые retries, отмена, обработка отказа/обрезки.
- Проверки конфликтных случаев и CLI с раздельными offline/live-режимами.
- Общие документы и контракт сохранены; отдельные AI-типы не заведены.

Реализованы HTTP-обработчики, PostgreSQL и миграции, расчёт навыков/допуска/фактов,
авторизация, атомарный импорт, симуляции и Docker-поставка. Frontend работает с этими
обработчиками. Источник сохраняется отдельно от выбранных целей и симуляций.

## Инварианты AI

- Числа, допуск и текст фактов создаёт доменное ядро. Модель выбирает только ID.
- candidate_id отличает конкретную попытку/сессию от event_id; не терять participation_id.
- Минимум три категории доказательств обязательны и для AI, и для fallback.
- Неполные evidence вызывают ошибку построения snapshot, а не красивый ответ без оснований.
- Резервное ранжирование учитывает только оставшийся целевой разрыв; прирост вне цели
  и выше требования не повышает балл. Условная польза prerequisite не становится заработанным навыком.
- Карточки — альтернативные следующие шаги, их эффекты не суммируются.
- Пустой набор требует доменной emptyReason. Не угадывать её внутри AI.
- После await нужна проверка DomainVersion в сервисе, даже при fallback.
- Живой AI, его преимущество и end-to-end скорость пока не подтверждены.

## Что делать дальше

1. Backend уже строит snapshot и обе карты BaselineSignals, проверяет сессию,
   ограничивает параллельный подбор и повторно проверяет версию после ответа.
2. Проверить живой AI: добавить ключ и модель в корневой `.env`,
   выполнить `npm run smoke:ai`, затем `npm run eval:ai -- --live`.
   Ключ не отправлять в чат, не хранить в Git, не печатать в логах.
3. Проверить полный каталог и отдельный зафиксированный набор профилей;
   измерить релевантность, latency, fallback, а не только валидность JSON.
4. Перед сдачей воспроизвести запуск и сценарий employee → completion → HR → import
   по корневому README на машине участника или жюри.

## Команды проверки

Из корня репозитория:

```sh
npm test
npm run typecheck
npm run build
npm run eval:ai
```

`npm run smoke:ai` и `npm run eval:ai -- --live` отправляют только авторские синтетические
примеры и требуют ключ. В offline-режиме обращений к провайдеру нет.
Командные AI-проверки первоначально выполнялись в Windows на Node 24.18.0.
После интеграции проверены macOS/Node 24 и Linux ARM64 Docker, включая PostgreSQL
и сохранение состояния при перезапуске. Другие платформы отдельно не проверялись.
