## Браузер и перезапуск

Production-сборка запущена через `npm run demo:start` на `localhost:3212`.
`demo:prepare -- --port=3212` создал отдельную схему с авторским набором
из `backend/tests/fixtures/ai-flow.ts`. Внешний AI в этой репетиции выключен.

Проверены реальные действия в браузере:

1. Вход сотрудником, цель Data Engineer Junior → Middle, SQL 1, покрытие 33%.
2. Детали SQL foundations и явно названное моделирование выполнения.
   Сохранён SQL 2, покрытие 67%, открылся Advanced SQL practice.
3. Второе выполнение: SQL 3, 100%, состояние достигнутой цели и следующее действие.
4. Обновление страницы сохранило результат. HR увидел одного сотрудника,
   два симулированных завершения и нулевой разрыв SQL.
5. В просмотре HR отсутствуют действия изменения цели и прохождения за сотрудника.
   Каталог показывает роль, грейд и предварительный SQL ≥2.
6. Сервер остановлен, после новой сборки запущен без `demo:prepare`.
   Сессия открыла `/hr`, два завершения сохранились.
7. Через HR выбраны авторские JSON-профиль и CSV-история. Предварительная проверка
   показала один профиль и одну запись без сохранения; обычный импорт подтвердил
   запись. Новый профиль появился в списке сотрудников; завершение из истории
   дало SQL 2, покрытие 67% и рекомендацию Advanced SQL practice.
8. При ширине 390 px профиль читается, переключатели разделов переносятся;
   после визуальной проверки восстановлен обычный viewport. Это один проверенный
   экран, не полный аудит всех мобильных состояний.

Ошибок `console.error` в проверенном браузерном проходе не обнаружено.
В серверном логе один GET импортированного профиля занял **2811 мс** во время
параллельных локальных проверок; это превышает целевой бюджет интерфейса.
Причина не изолирована: нельзя ни объявить SLA выполненным, ни приписать задержку
конкретному запросу БД без замера. Нужен отдельный повтор под контролируемой нагрузкой.
Показ и импорт относятся только к авторским данным. Реальное обучение,
провайдер в браузере, UI ≤2 с под нагрузкой и полный AI SLA ≤10 с не измерялись.
Импорт добавил второй тестовый профиль в текущую репетицию; для чистого
трёхминутного показа создать новую схему через `demo:prepare`.

## Исправленные неуспехи и пределы

Первый запуск клиентских проверок после объединения дал две ошибки:
`Cannot read properties of undefined (reading 'join')` в неполном тестовом
каталоге и поиск старой кнопки «Отметить активность выполненной».
Fixture дополнен обязательными полями, ожидания обновлены на явную симуляцию,
добавлены проверки условий и отсутствия действий у HR. Итоговый набор выше прошёл.

Критический агент нашёл конфликт URL `options` с изоляцией схемы и отсутствие
условий допуска в каталоге. Оба замечания исправлены: небезопасная комбинация
`DATABASE_URL`/`DATABASE_SCHEMA` отклоняется до bootstrap, условия видны в UI.
Восемь тестов конфигурации входят в итоговый backend-набор.

Не заявлены: независимая HR-оценка, полное покрытие каталога, доказанный эффект
на вовлечённость, нагрузочный браузерный SLA, повторная сборка Docker image,
развёрнутый публичный стенд или зелёный CI. По ТЗ публичный URL, LMS и SSO
не являются обязательными артефактами; настройки перед внешним пилотом всё равно нужны.

Локальные консольные логи находятся в игнорируемом `test-results/`:
`jury-publish-tests.txt`, `jury-publish-build.txt`, `jury-publish-build-final.txt`,
`jury-publish-build-last.txt`, `jury-publish-client-last.txt`, `jury-publish-integration.txt`,
`jury-publish-live-flow.txt`. Публикуются только явно выбранные авторские JSON-отчёты
и агрегатный аудит без идентификаторов исходных сотрудников.
